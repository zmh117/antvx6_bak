# 业务图泳道闪烁根因修复（修正版）

## 一、真正的根因（与原计划不同）

症状：把泳道从 A 拖到 B，松手后泳道先闪回 A、再跳到 B，看着像卡顿。

这不是渲染开销问题，而是**整张 X6 画布在每次自动保存时被销毁重建**：

- 创建画布的主 `useEffect`（[front/src/features/business-flow-editor/index.tsx](front/src/features/business-flow-editor/index.tsx) 223-353 行）依赖数组为 `[businessFlowId, schedulePersist]`，cleanup 里执行 `graph.dispose()`。
- `schedulePersist` → `persistCanvas` → `runPersistCanvas`，后者依赖 `applyChangesMutation`（190 行）。
- `useApplyBusinessFlowChangesMutation`（[queries.ts](front/src/entities/business-flow/api/queries.ts) 277-293 行）返回 useMutation 结果对象，其引用在 `idle→pending→success` 状态切换时会变。
- 于是：松手 → 保存进入 pending → mutation 引用变 → `schedulePersist` 引用变 → 主 effect 重新执行 → `graph.dispose()` 重建并用 `canvasRef.current`（此刻仍是旧位置 A）重渲染 → 闪回 A；保存成功后 canvasRef=B 且 mutation 转 success 引用再变 → 再次重建 → 跳到 B。

## 二、修复（最小、精准）

仿照同文件已有的 `persistCanvasRef`（211-213 行）ref 模式，把 persist 回调从画布生命周期 effect 中解耦：

- 新增 `const schedulePersistRef = useRef(schedulePersist)`，并用一个 `useEffect` 保持其指向最新的 `schedulePersist`。
- 将主 effect 内所有 `schedulePersist()` 调用替换为 `schedulePersistRef.current()`（涉及 `node:moved`、`node:resized`、`edge:connected`、`edge:removed`、`node:removed`、键盘删除等处）。
- 主 effect 依赖数组从 `[businessFlowId, schedulePersist]` 改为 `[businessFlowId]`，使画布仅在切换业务图时重建。
- 保留 `node:change:position` 的 `options.translateBy !== node.id` 守卫，消除拖动过程中每帧 N 次 `fitLaneToChildren` 的冗余开销（非闪烁主因，但有益）。

## 三、验证

- 拖动泳道 A→B 松手：不再闪回 A，直接停在 B；保存仍正常落库、版本递增。
- 切换到另一个业务图再切回：画布正常加载（确认 `[businessFlowId]` 依赖未破坏重载）。
- 含 10+ 节点的泳道拖动流畅；单节点拖动仍实时撑大泳道；历史/恢复正常。

## 四、其余改进项（保持原计划 A/B/C/D 不变）

- A 后端 Agent 上下文打包迁移到 DDD query handler + repository，services 仅留 shim。
- B 业务图文档写入 `er_search_document`，统一检索层。
- C 补齐节点级 ER 绑定（erRefs / step_key→node）。
- D 业务图编辑器分层（hook、ops diff 下沉、Inspector/History 抽组件），并确认后端 apply_changes 的乐观锁与不变量兜底。
